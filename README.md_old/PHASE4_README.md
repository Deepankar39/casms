# CASMS — Phase 4 batch: Integrity and Transaction Handling

**Prerequisites:** Run and verify 01_schema.sql, 02_seed.sql, 03_basic_queries.sql, 04_analytics.sql, 05_views.sql, 06_functions_procedures.sql, 07_triggers.sql and 10_indexes_explain.sql on MySQL 8.0.46. Use a local administrator connection for Phase 4 setup. Close any interrupted transaction before starting.

Copy `phase4_concurrency_lab.md` to `docs\` and `phase4_backup_restore.ps1` to `database\`.

## Execute in this exact order

1. `08_transactions.sql`: simple COMMIT/ROLLBACK/SAVEPOINT, creates tagged lab fixtures, runs one successful close and one expected failed close; initializes a two-row concurrency lab in `casms_perf`.
2. `09_integrity_tests.sql`: 10 negative tests (expected violations **caught** in a stored test runner); expected **10 PASS, 0 FAIL**.
3. `11_security_users.sql`: run as MySQL administrator. Creates/rotates `casms_app` and `casms_report` random local passwords and assigns minimum rights. **Copy generated passwords privately from Result Grid; never post them in ChatGPT or commit them.** Rerunning rotates passwords!
4. `12_final_validation.sql`: read-only checks: **22 CASMS base tables, 7 views, 4 functions, 6 procedures, 14 triggers, 50,000 performance rows**, plus closure and integrity checks. Phase 4 fixtures add +1 asset, +3 requests, +1 maintenance record, +1 part relative to Phase 2.
5. `phase4_concurrency_lab.md`: **manual**, in two independent Workbench connections. Follow each interleaving in the stated order. A single “Execute All” cannot demonstrate concurrency.
6. `phase4_backup_restore.ps1`: run from PowerShell **after** MySQL CLI utilities are installed and reachable. Requires local administrator password (prompted by MySQL client) and creates a **separate restore database**, without dropping your working `casms` database. If your MySQL client cannot process `SOURCE` paths containing spaces, use Workbench's Server → Data Import for the generated SQL file into a fresh schema. Compare row counts. Preserve backup files privately.

## What a successful run looks like

- `P4-CLOSE-OK`: status `Closed`, exactly one maintenance record and one part.
- `P4-CLOSE-FAIL`: status `In Progress`, zero maintenance records and parts after the intentionally bad part quantity.
- `P4-CONCURRENCY`: remains `In Progress` unless you performed the optional real-closure race.
- Integrity checks: 10 tests, all PASS.
- Base schema/object counts as above.
- Backup restored in a **different** schema, matching row counts.

## Known boundaries

- These scripts cannot themselves certify that the Node.js/Express app is secure; backend role enforcement must be tested in Phase 5/6.
- Business-rule triggers protect key invalid transitions, but some real-world edge cases require integration testing.
- Temporary accounts generated by `11_security_users.sql` must be stored in a local `.env` (gitignored) when Phase 5 is set up. MySQL session storage is created/granted later during authentication setup.
- `CREATE/ALTER USER` needs appropriate MySQL administrator privileges. Use your local root connection.
- Do not claim a phase completed until you share the actual MySQL outputs and the manual lab/backup results.
